# Module Config — Non-Obvious Constraints

## C1: KEY_ID and KEY_SECRET are required — format not validated

**Rule:** Both `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` must be non-empty to save settings.
**Why:** Without them, `getRazorpayApiInstance()` constructs an `Api($KEY_ID, $KEY_SECRET)` call that will fail at the first Razorpay API call. The module shows an admin warning when either is null at construct time.
**Enforced at:** `razorpay.php:_postValidation()` — uses `empty()` check only. No prefix check (e.g., `rzp_live_` vs `rzp_test_`), no length check, no character validation. Wrong keys pass validation and fail later at runtime.
**Gotcha:** Keys are `null` (not empty string) until first save. `array_key_exists` is used in `__construct()` rather than `isset()`, so a config row with a null value would still be loaded as null. The warning fires when either key `=== null`.

## C2: RAZORPAY_WEBHOOK_EVENTS stored as raw POST value — no JSON enforcement in PHP

**Rule:** Webhook events are saved verbatim from `Tools::getValue('EVENTS')`.
**Why:** The admin template (admin.tpl) constructs and submits the events as a JSON-formatted string. The PHP side does no parsing or validation — `Configuration::updateValue('RAZORPAY_WEBHOOK_EVENTS', Tools::getValue('EVENTS'))` stores whatever string arrives.
**Enforced at:** The browser/template layer only. If the form is bypassed or the template changes, malformed JSON can be stored.
**Supported event names (hardcoded in razorpay.php):**
- `payment.authorized`
- `payment.failed`
- `order.paid`
**Default enabled events** (property `$webhookEvents`): `payment.authorized` and `order.paid` — `payment.failed` is in `$webhookSupportedEvents` but NOT in `$webhookEvents` default, so it is off by default.

## C3: 24h webhook verification TTL — does not exist as a code gate

**Rule:** There is NO 24h TTL guard in the current code.
**Why this matters:** `RAZORPAY_WEBHOOK_LAST_VERIFY` is written after a successful `autoEnableWebhook()` call, but it is never read in `_postProcess()` or `autoEnableWebhook()`. Every admin settings save triggers a full webhook registration attempt regardless of when the last one ran.
**Enforced at:** Nowhere — the field exists but is only written, never read for throttling.
**Gotcha:** Merchants who save settings frequently will make repeated Razorpay webhook API calls. This is bounded only by Razorpay's own rate limits.

## C4: Private/localhost IP blocks webhook registration

**Rule:** If the shop domain resolves to a private or reserved IP address, webhook auto-registration is silently skipped and `ENABLE_RAZORPAY_WEBHOOK` is set to `'off'`.
**Why:** Razorpay cannot reach a private IP to deliver webhook events. Attempting registration would create an unreachable webhook endpoint.
**Enforced at:** `razorpay.php:autoEnableWebhook()` — `filter_var($domain_ip, FILTER_VALIDATE_IP, FILTER_FLAG_IPV4 | FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE)`.
**Exact check:** IPv4 only (`FILTER_FLAG_IPV4`). IPv6 private addresses are not checked — a shop on an IPv6-only private network would pass this gate and attempt registration.
**Blocked ranges:** RFC1918 private ranges (10/8, 172.16/12, 192.168/16), loopback (127/8), link-local (169.254/16), and IANA reserved ranges.
**Side effect on failure:** A log entry at severity 3 is written: `"Could not enable webhook for localhost"`. No user-facing error is shown in the admin UI.

## C5: Webhook URL format and construction

**Rule:** The webhook URL is generated by PrestaShop's link helper, not hardcoded.
**Construction:** `$this->context->link->getModuleLink('razorpay', 'webhook', [], true)` — the final `true` forces HTTPS.
**Resulting URL shape:** `https://{shop-domain}/module/razorpay/webhook`
**Enforced at:** PS link helper. The domain comes from PS shop configuration, not `$_SERVER['HTTP_HOST']`.
**Exact-match requirement:** Webhook URL matching against Razorpay's list is strict string equality (`===`). If the shop domain changes (e.g., HTTP to HTTPS migration, subdomain change), the old webhook URL will not match and a new webhook will be POST-created, leaving orphaned webhooks in Razorpay.
**Display in admin form:** The same `getModuleLink` call is used to show the URL in the admin form template (`_displayForm()` assigns `webhookUrl`), so what the admin sees matches what gets registered.

## C6: Payment action values — "capture" is default when empty

**Rule:** Only `"capture"` and `"authorize"` are valid values for `RAZORPAY_PAYMENT_ACTION`.
**Why:** These map to Razorpay API's payment capture modes. Any other value would silently fall back to capture behavior in downstream processing.
**Enforced at:** `_displayForm()` — the Smarty template receives the two constants (`self::CAPTURE = 'capture'`, `self::AUTHORIZE = 'authorize'`) and renders them as a dropdown. No server-side validation of the submitted value in `_postValidation()`.
**Default when empty or null:** `_displayForm()` uses `($this->PAYMENT_ACTION === self::CAPTURE || !$this->PAYMENT_ACTION) ? "selected='selected'" : ""` — the capture option is pre-selected if `PAYMENT_ACTION` is falsy (null, empty string, or unset). This means a fresh install with no saved config will present "Authorize and Capture" as the selected option.
**Gotcha:** `_postProcess()` saves `Tools::getValue('PAYMENT_ACTION')` verbatim. If the form submits an empty string (edge case), `"capture"` is NOT written — an empty string is stored. The UI default logic handles display correctly, but downstream code reading this config key must also handle empty string as capture.

## C7: WEBHOOK_WAIT_TIME default is 300 seconds

**Rule:** If `WEBHOOK_WAIT_TIME` is not submitted or is falsy, it defaults to 300 seconds.
**Why:** This is the timeout the webhook processor waits before assuming a payment confirmation from the frontend was missed. 300 seconds (5 minutes) is a balance between waiting long enough for slow networks and not holding DB locks indefinitely.
**Enforced at:** `razorpay.php:_postProcess()` — `$webhookWaitTime = Tools::getValue('WEBHOOK_WAIT_TIME') ? Tools::getValue('WEBHOOK_WAIT_TIME') : 300`. Also defaulted in `_displayForm()` for display: `$this->WEBHOOK_WAIT_TIME ? $this->WEBHOOK_WAIT_TIME : 300`.
**No upper bound enforced:** Any integer value is accepted and stored. Extremely large values could cause webhook processing to stall for impractical durations.
